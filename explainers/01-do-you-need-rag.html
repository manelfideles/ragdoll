Explainer 01 · RAG

Do you even need RAG?

Before you build a retrieval pipeline, you must prove you need one. This is the first discipline of RAG engineering, and it changes the shape of your medical coding project.

RAG means Retrieval-Augmented Generation. You search a set of documents for the passages that match a question. You put those passages into the prompt. The model answers from them. That is the whole idea.

People call RAG an AI technique. It is not. It is a search technique with a language model attached to the end. Almost every RAG failure is a search failure. Keep this sentence in mind for the rest of the project.

The baseline pipeline

Anthropic's engineering team describes the standard pipeline in six steps. Learn these names. Every later lesson attaches to one of them.

  1. Chunk. Cut each document into small pieces.
  2. Embed. Turn each chunk into a vector. A vector is a list of numbers that records meaning.
  3. Index for keywords. Build a BM25 index. BM25 is a classic algorithm that scores exact word matches.
  4. Search by meaning. Embed the question. Find the chunks with the nearest vectors.
  5. Fuse the ranks. Merge the keyword results and the meaning results into one ordered list.
  6. Stuff the prompt. Put the top chunks into the prompt and ask the model.

The rule that may cancel your pipeline

Anthropic state a threshold plainly:

If your knowledge base is smaller than 200,000 tokens (about 500 pages of material), you can just include the entire knowledge base in the prompt.

A token is a piece of a word. Roughly 750 words make 1,000 tokens. Modern Claude models accept very large prompts, and prompt caching makes the repeated cost small. Prompt caching stores the processed prompt on the server so you do not pay full price to send the same documents again.

Now apply the rule to your project. The ICD-10-CM Official Guidelines for FY 2026 is about 120 pages. That is far under 500 pages. One coding guideline document does not need RAG. You could paste the whole thing into the prompt and get better answers than a badly built pipeline.

What this means for ragdoll

This is not a reason to abandon the project. For a platform it is something better: a feature.

Ragdoll never knows in advance how large a project will be. One user uploads a single memo. Another uploads four hundred contracts. A pipeline that retrieves is wrong for the first user and necessary for the second. So ragdoll should measure each project and choose:

  • Under the threshold. Skip retrieval. Put every document in the prompt and lean on prompt caching. Fewer moving parts, and no chance of retrieving the wrong passage, because there is no retrieval to get wrong.
  • Over the threshold. Run the full pipeline.

Almost no RAG side-project does this. Most retrieve unconditionally, including over corpora small enough to fit in one prompt. Building the threshold check makes ragdoll defensible in a way a wrapper around a vector database is not, and it gives you a real answer to the hardest interview question: when did you decide not to use RAG?

Two more things justify the pipeline once you are over the threshold, and both are platform concerns rather than retrieval concerns: project isolation, so one project's chunks never surface in another project's search, and citations, because retrieval hands you the source passage as an object you can link to. Write all of this in your README.

Why naive chunking fails

Step 1 looks trivial. It is the largest source of failure. When you cut a document into pieces, each piece loses the story around it.

A concrete example from the test corpus

Imagine a chunk that reads:

"Assign code 250 only when the condition is documented as the reason for the encounter. Do not assign it as an additional diagnosis."

Search for "can I code diabetes as a secondary diagnosis" and this chunk may never appear. The chunk does not say diabetes. It does not say secondary. It does not say which chapter or which fiscal year it belongs to. The context lived in a heading three pages up, and chunking threw the heading away.

The fix is contextual retrieval. Before you embed a chunk, you ask a cheap model to write 50 to 100 tokens that explain where the chunk sits. You put that text in front of the chunk. Then you embed and index the combined text. The chunk now carries its own context.

What actually moves the needle

Anthropic measured each change on the same task. The metric is the failure rate of retrieval: the share of questions where the correct passage did not come back in the top 20 results. Lower is better.

Embeddings + BM25 (baseline)5.7%—
+ contextual embeddings3.7%35%
+ contextual embeddings + contextual BM252.9%49%
+ reranking1.9%67%

Reranking is a second, slower scoring pass. You retrieve a wide set, perhaps 150 chunks. A reranker model scores each one against the question. You keep the best 20. You get accuracy without paying to put 150 chunks in the prompt.

Read the table again and notice what is absent. No change of language model. No clever prompt. Every gain came from the search half of the system.

Why you build the test set first

The table above only exists because someone could measure failure. You cannot improve retrieval you cannot score. So the first thing to build is not the ingestion pipeline. It is the golden set: a list of questions, each paired with the passage that truly answers it.

With a golden set you can compute recall@k. Recall@k asks: of all the passages that truly answer the question, how many appeared in the top k results? This one number tells you whether a change helped or hurt. Without it, you are guessing, and every RAG tutorial you read is guessing with you.

The order of work

Golden set → measure the dumbest possible pipeline → change one thing → measure again. Never change two things at once. This is the loop that turns a side-project into portfolio evidence, because it produces sentences like "recall@5 rose from 0.61 to 0.84 when I added contextual embeddings."

Check yourself

Question 1

A ragdoll user creates a project and uploads one 40-page memo. What should ragdoll do?

Correct answer: the second. Under roughly 200,000 tokens, stuffing the prompt is legitimate and usually better, because retrieval cannot fetch the wrong passage if there is no retrieval. Ragdoll should measure each project and choose. Knowing when not to retrieve is the mark of someone who has built this before.
Question 2

A coder asks about secondary diagnoses. The correct passage exists but never comes back in the results. Where do you look first?

Correct answer: the third. The passage never reached the prompt, so the model and the prompt cannot be at fault. This is a search failure. Chunking is the usual cause.
Question 3

What does contextual retrieval add to a chunk before indexing it?

Correct answer: the fourth. A short generated preface travels with the chunk into both the vector index and the BM25 index. Overlap is a different and weaker technique.
Question 4

You keep both a vector index and a BM25 index. Why keep BM25 at all?

Correct answer: the first. This matters enormously in medical coding. Embeddings capture meaning and lose precision on identifiers. BM25 scores literal word matches. Fusing both is called hybrid search, and it is the reason the baseline in the table already includes BM25.
Question 5

Reranking cut the failure rate from 2.9% to 1.9%. Why not simply put all 150 retrieved chunks in the prompt instead?

Correct answer: the second. A reranker is the cheap filter between wide retrieval and a narrow prompt. Reranking buys accuracy; keeping the prompt narrow buys speed, cost, and focus.
Question 6

It is your first evening on the project. Two hours. What do you build?

Correct answer: the third. Every other choice produces work you cannot score. The golden set is what makes the following ten sessions measurable, and it is the artefact that most reviewers of your portfolio will recognise as real engineering.
